## Entity identifier strategy

Entity primary keys use PostgreSQL `BIGINT GENERATED BY DEFAULT AS IDENTITY`, with independent sequences for accounts, workspaces, memberships, OAuth identities, invitations, knowledge tickets and refresh sessions. Java entities and repositories use `Long`. Verification email rows use the account ID as their shared primary/foreign key rather than generating another ID. Foreign keys and scalar ownership references use the same bigint type.

The server assigns entity IDs when persisting new rows. Identity sequences may have gaps, including after failed transactions; IDs are neither chronological business numbers nor authorization credentials. Every protected operation continues to enforce active account and workspace membership/role checks.

API entity identifiers are decimal strings in JSON and remain strings in frontend models, URLs, workspace headers and email links. This preserves the full signed bigint range without JavaScript number rounding. Numeric pagination orders by creation timestamp and numeric ID, and uses version 2 cursors. Refresh cookies pair the numeric session ID with an independently random 256-bit secret; only secret hashes are stored.

Submission IDs remain UUIDs for retry deduplication under the unique `(AUTHOR_ID, SUBMISSION_ID)` constraint. Email attempt IDs and classification lease tokens remain UUIDs to distinguish worker claims. Provider subject identifiers retain their provider-defined string representation. ShedLock uses its existing named key.

The original Liquibase SQL initialization scripts create bigint entity keys directly; there is no UUID-to-bigint conversion migration. This development-only rewrite assumes no application tables or Liquibase history. Before using it against any existing development database, stop backend instances and explicitly execute the application's manual `db/reset-development.sql` script in that database. Deleting rows alone does not reset schema types or applied checksums.

The reset script drops child tables before their referenced parents, then removes application trigger functions and Liquibase history. Owned identity sequences are dropped with their tables. It keeps the `public` schema and unrelated tables, avoids `CASCADE`, and rolls back if unexpected dependencies prevent removal. The backend never runs the reset automatically. On restart, Liquibase recreates the tables, foreign keys, indexes and sequences from the rewritten initialization scripts.

Deploy matching backend and frontend after reset and discard old IDs, links, refresh cookies and cursors. A populated production migration would require a separate data-preserving plan.
